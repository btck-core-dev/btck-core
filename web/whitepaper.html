1. Design principles

VERIFIABLE SCARCITY

All subsidy issuance is determined in integer SatK by consensus.

SEPARATE COMPUTE LAYERS

ASICs secure L1. GPUs sell useful work on L2 and cannot mint BTCK.

MACHINE-NATIVE ACCESS

Agents are intended to buy individual services under explicit wallet policies.

ZERO GENESIS REWARD

Genesis creates no spendable BTCK and imports no DEVNET balance.

DISCLOSED GUARDIAN PHASE

Controlled early hashrate is disclosed rather than described as an open launch.

VERIFY, DO NOT TRUST

Network data, artifacts, hashes and limitations must remain independently checkable.

4. Combo selection and maturity

Each Combo window records valid L1 candidate blocks. One hundred blocks after the window closes, the beacon is derived from the future consensus block:

beacon = SHA256(block_hash[window_end + 100] || epoch_index_uint64_le)
winner = argmin(candidate_block_hash XOR beacon)

Every valid block has one candidate entry. Splitting rewards across many addresses does not create additional chances. Long-run probability remains proportional to valid block production.

5. Disclosed guardian launch

The first 271,828 blocks are mined under controlled project hashrate. This reduces cold-start exposure to immediate majority-hashrate reorganization on an algorithm with a large existing hardware base. It is not described as an open-from-genesis fair launch.

  • Genesis reward is zero and no DEVNET balance is imported.
  • Every guardian coin is created by valid kHeavyHash work under the same year-one 80/15/5 rules.
  • The hash of block #271,828 will be frozen into public node releases.
  • The controlled hashrate, receiving outputs and reserve governance must be disclosed before public ports open.

6. Security after issuance

Blocks continue after the four-year subsidy ends. From block #126,144,001, actual transaction fees are divided permanently: 50% to the immediate block miner and 50% to the permanent Combo reserve. There is no tail emission and no renewed ecosystem subsidy.

6.1 The primary mission: an open Agent economy

Bitcoin K is not intended to stop at issuing a scarce proof-of-work asset. L1 is the neutral settlement and security foundation; the project's principal economic expansion is L2: a competitive market in which independent GPU operators load useful models and autonomous agents purchase inference one job at a time.

This changes the customer from a human clicking a subscription page into software that can discover a model, compare a signed quote, enforce its own budget, pay, verify delivery and continue working. A user who cannot pass a platform's account, region, card or KYC gate should still be able to fund a local agent and buy a narrowly scoped service without surrendering the agent's wallet keys.

L1: SECURITY

ASIC miners order transactions and make SatK settlement expensive to rewrite.

L2: PRODUCTIVE SUPPLY

GPU providers turn idle or dedicated hardware into model endpoints with measurable service quality.

AGENTS: DEMAND

Software purchases only the intelligence it needs under explicit owner policies.

6.2 One Agent call, end to end

Discover

The agent requests offers by model family, context size, jurisdiction, latency, privacy policy and maximum price.

Quote

Providers return signed offers denominated in integer SatK with model-weight hash, benchmark class, expiry and service limits.

Authorize

The local policy wallet verifies service scope, per-call ceiling, daily budget and delegation expiry. Default is deny.

Challenge and pay

An HTTP 402 invoice binds amount, destination, nonce and expiry. The wallet signs locally; neither gateway nor provider receives a recovery phrase.

Route privately

The encrypted request is sent to the selected provider. A future relay profile can prevent the provider learning the client's home IP.

Prove delivery

The provider returns the result and a signed receipt containing job identity, model commitment, timing and metering evidence.

Settle and distribute

Paid SatK is divided by the active L2 schedule among the GPU provider, standby capacity, AI Combo, burn and ecosystem support.

This is the target production architecture. HTTP 402 settlement, provider discovery and DEX/liquidity routing are not live on mainnet today.

6.3 Private robot wallets

A robot wallet is not a hot wallet with unlimited authority. It is a constrained execution wallet controlled by a human or organization. The principal signs a delegation pact; the machine can spend only inside that pact. A delivery robot may buy charging but not exchange assets. A research agent may buy an approved model call but not transfer its entire balance.

8. GPU readiness and ecosystem reserve

The planned provider market uses unpredictable inference probes, job receipts and observable quality. Candidate signals include model identity, weight hash, quantization, time-to-first-token, throughput, completion rate, hardware class and quoted price. Slashing and reputation require a public testnet and adversarial review before production.

The 5% L1 ecosystem output is intended to support security review, open tooling and carefully disclosed GPU cold-start programs. No fixed 500-BTCK daily subsidy is active today. Any future program requires a published budget, objective recipient rules, reserve balance reporting and on-chain records. The protocol promises neither fiat returns nor guaranteed provider income.

9. Machine payments

The experimental HTTP 402 profile describes single-use invoices denominated in integer SatK. A challenge binds an invoice identifier, amount, destination, nonce and expiry. Payment proofs use canonical digests, signatures and idempotency keys. Direct balance mutation endpoints are disabled in production profiles.

WWW-Authenticate: L402 invoice="…", currency="SatK", amount="…"
X-Payment-Address: btck1s…
X-Payment-Network: BTCK-BlockDAG
X-Payment-Expires: unix_timestamp

An off-chain service layer may represent 1 SatK = 1,000 mSatK for sub-SatK accounting. On-chain consensus remains denominated in integer SatK.

10. Policy-bound agent wallets

The delegated wallet profile is designed for software and physical robots. A principal authorizes a narrowly scoped agent identity with allowed services, a maximum per payment, a rolling budget and an expiry. Default behavior is deny. Spending keys remain client-side or inside a hardware enclave.

  • A server must never request a recovery phrase or private spend key.
  • A prepared signature is not represented as settled until independently verified.
  • Stealth outputs reduce address linkage; they do not hide IP metadata.
  • Production use remains blocked pending wallet review and end-to-end settlement tests.

12. Risks and verification

Bitcoin K is experimental software. Proof-of-work networks face software defects, hashrate concentration, economic attacks, operational failure and regulatory uncertainty. Stealth addresses are not a substitute for a complete privacy audit. Token ownership does not promise profit, yield or future service access.

Public evidence should include source and release tags, reproducible build instructions, artifact hashes, an SBOM, genesis parameters, checkpoint #271,828, known limitations, reserve addresses and independent security findings.
