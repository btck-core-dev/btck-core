# BTC-K L2 生产彩排与审计交接清单（2026-10-09）

## 当前结论

L2 代码可以进入**候选审计与真实小额彩排准备**，但仍保持生产关闭。L1 主网、矿池和现有钱包服务不需要因本清单停机或改配置。

## 已冻结的最小生产架构

1. 公网网关只保存 L2 Treasury 公共隐身地址，不保存助记词、spend key、view key 或钱包密码。
2. 充值由网关通过 canonical L1 RPC 验证唯一发票输出和确认深度。
3. 提现与销毁没有公网 HTTP 入口，只能由独立结算操作读取审批记录后执行。
4. 首发价格使用版本化的整数 SatK 服务目录；动态法币/交易所预言机不启用。
5. 所有生产交易至少达到与充值相同的确认门槛后才标记完成。
6. 任意 ChainId、高度、账本、签名、确认深度或持久化异常均 fail closed。

## 需要持有人亲自完成的金库仪式

这些步骤不能由开发机代替，也不能自动生成后把恢复词写进日志：

1. 在离线环境生成一个全新的 `BTC-K L2 Treasury` 钱包。
2. 手写恢复词并完成恢复验证；不得复用个人、矿池或生态基金钱包。
3. 只把公共隐身地址交给公网网关配置。
4. 加密钱包文件放在独立结算主机或离线介质，权限 `0600`；密码不与钱包文件同机明文保存。
5. 先仅注入可承受损失的极小额 BTC-K 和独立网络费储备。

## MAINNET 小额彩排顺序

严格使用新建 L2 Treasury 和测试 Agent，且生产 L2 对公众继续关闭：

1. 记录开始高度、ChainId、源地址、Treasury 公共地址和候选 Git commit。
2. 创建一张最小金额发票，付款后等待配置确认数，确认只能入账一次。
3. 注册一台签名 GPU worker，完成一次真实推理，核对五方分账总和严格等于实际扣款。
4. 重启网关，确认发票、余额、settlement ID 和 outpoint replay guard 均保留。
5. 提取一笔最小金额到全新测试钱包；在浅确认阶段必须显示 `BROADCAST`，达到门槛后才显示 `CONFIRMED`。
6. 广播一笔最小 NUMS 销毁；核对金额、固定 `(R,P)`、txid、独立费用储备及浏览器可见性。
7. 在一次广播后、收到结果前中断结算进程；重启后必须对账/重播同一 txid，不能二次扣款。
8. 导出不含密钥的 JSON 证据：高度、txid、vout、确认数、分账、余额前后值、代码提交和测试摘要。

任何一步失败都立即停止，不扩大金额，不开放公网 L2。

## 提现与销毁策略待签字项

在真实资金进入前，由项目持有人书面确定：

- 单笔提现上限和 24 小时累计上限；
- 大额提现等待时间；
- 单人还是双人审批，以及审批证据保存方式；
- 紧急暂停负责人和触发条件；
- 网络费储备下限与补充流程；
- 日常对账频率和余额差异容忍值（建议必须为零）。

在这些值尚未签字前，不应把任意猜测值写成“正式规则”。

审计候选必须绑定一个干净 Git commit。审计方至少应获得：

- `docs/45_BTCK_L2_CHAIN_SETTLEMENT_AND_GPU_HARDENING_2026-10-09.md`；
- 本文件；
- `src/gateway/ai_rpc_gateway.py` 与 `src/gateway/l2_chain_bridge.py`；
- `src/privacy/`、`src/tokenomics/provable_burn.py`、`src/worker/pricing_engine.py`；
- 节点交易 RPC 与全部 L2/x402/GPU/钱包测试；
- 全量测试日志、候选 commit、文件 SHA-256 和真实小额彩排的去密钥证据。

审计人员必须独立于本轮实现者。内部测试和本文件不能被描述为“独立安全审计”。
