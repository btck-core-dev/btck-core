## 5. 抗女巫与防狙击开奖算法：未来随机信标 + XOR 几何距离测距

为杜绝传统抽奖机制中大矿工通过分拆千万级临时地址（Sybil Attack）刷高中奖率的作弊行为，BTC-K 采用基于密码学哈希空间的未来信标测距：

1. **蓄水期**：在周期内（如 43,200 块），所有出块矿工的有效区块哈希记录在链上；
2. **未来信标锁定**：周期结束后，强制等待 $100$ 个区块（约 100 秒确认）。候选块与信标块哈希均为主链共识验证后的 32 字节 **kHeavyHash PoW 值**；再严格按下式做一次确定性 SHA-256 域混合：
   $$H_{beacon} = \text{SHA256}(\text{BlockHash}_{H_{end}+100} \parallel \text{EpochIndex}_{uint64})$$
   其中 `EpochIndex` 固定使用 8 字节小端编码。不得改用 BLAKE3、不得额外拼接节点本地字段；所有实现必须通过同一固定测试向量。
3. **异或测距**：遍历计算过去周期内所有区块哈希与未来信标的异或几何距离：
   $$\text{Distance}_i = \text{BlockHash}_i \oplus H_{beacon}$$
4. **极值胜出**：$\text{argmin}_i(\text{Distance}_i)$ 的出块区块独揽当期头奖。
5. **密码学与博弈论客观评析（落实审计报告29整改意见）**：
   * **每个有效候选区块机会严格均等**：在 256 位均匀哈希空间中，每个有效区块与未知未来信标的 XOR 距离分布完全一致，没有任何区块具有先验优势；
   * **统计学期望与有效算力成正比**：矿工或矿池的长期中奖期望正比于其生产的有效区块份额（若某矿池产出全网 40% 的区块，其获得大奖的数学期望即为 40%），本算法消除的是“地址作弊”，而非否定物理算力的贡献；
   * **免疫地址女巫攻击**：开奖仅以链上真实产生的出块哈希为候选样本，矿工拆分成 1 个还是 10,000 个接收地址，对中奖概率产生 0 影响；
   * **杜绝提前定向算块**：未来信标在出块窗口关闭 100 块之后才诞生，任何算力都无法在挖矿期间获知信标靶心；
   * **散户与 Solo 矿工暗标逆袭**：散户矿工即便只挖出 1 个有效区块，在与未来信标的几何测距中，同样拥有一发入魂直接命中全网最小距离的真随机机会！

## 6. 双轨渐进式成熟锁仓机制（Progressive Dual-Track Maturation & Streaming Vesting）

### 6.1 轨道一：常规区块奖励渐进成熟期（Regular Block Progressive Maturation）
常规区块奖励不再采用脆弱固定的测试级参数，而是随网络发展阶段呈阶梯稳步递增，精准斩断短租快闪算力：

* **第 2 年**：**6 小时（21,600 块）**。日内批处理结算 4 次，适应产出衰减期，阻断跨时段套利；
* **第 3 年**：**24 小时（86,400 块）**。经典日结周期，对齐成熟金融级结算标准；
* **第 4 年**：**72 小时（259,200 块）**。3 日批处理结算，极大沉淀最终极稀缺阶段的日常流通盘。

### 6.2 轨道二：Combo 暴击大奖对称流式锁仓（Jackpot Streaming Vesting）
Combo 大奖锁仓成熟期与开奖周期严格按 **$4 \times \text{开奖周期}$** 保持 3 倍等比同频共振：

$$\text{大奖成熟锁定期} = 4 \times \text{开奖周期}$$

* **Phase 2 (第2年)**：锁仓 **144 小时（6 天 / 518,400 块）**：

  - **分批释放 (75%)**：分 3 批，每 48 小时释放 25%（日均释放约 411 枚）；
* **Phase 3 (第3年)**：锁仓 **432 小时（18 天 / 1,555,200 块）**：

### 8.5 KCU 价值桥、毫聪（mSatK）精度与统一钱包显示

L2 服务不得把某个固定 SatK 数字永久当作模型价格。协议使用 **KCU（Knowledge Compute Unit）** 作为模型工作量与商业价值之间的中间计价单位：

$$1 \text{ KCU} = \$0.00010 \text{ 的默认参考服务价值}$$

模型、Token 数、输出计算权重、量化方式和服务等级先决定 Task KCU，再使用公开的 BTC-K 参考价格换算：

$$\text{Task mSatK} = \left\lfloor \frac{\text{Task KCU} \times 10,000,000}{P_{BTCK}} + 0.5 \right\rfloor$$

因此，同一任务在 BTC-K 升值时消耗更少 SatK，在 BTC-K 贬值时消耗更多 SatK；Task KCU 本身不随币价改变。启动期没有足够市场深度时，`bootstrap-fixed-v1` 固定使用 `$0.05/BTC-K` 参考价，不得伪称为市场现价。只有在多市场流动性成熟、TWAP、中位数、过期保护、单日变动上限和异常停机经过审计后，才允许通过新的版本切换动态价格源。

为描述 BTC-K 在极端高币价下的亚 SatK 报价精度，协议定义毫聪（mSatK）扩展单位：

$$1 \text{ BTC-K} = 10^8 \text{ SatK} = 10^{11} \text{ mSatK (毫聪)}$$

* **精度边界**：
  - 当 $P_{BTCK} = \$100,000$ 时，单次 8B 推理（0.8 KCU = $0.000080）对应 **80 mSatK**（0.08 SatK）；
  - 当前 L1 与 L2 原型账本只结算整数 SatK，网关会保存 mSatK 报价并把发票向上取整到整数 SatK；因此不能宣称当前已经实现零舍入误差；
  - 真正的 sub-SatK 累计结算必须先完成持久化账本、并发一致性、提现换算与独立安全审计，未通过前不得在生产环境启用。

钱包没有 L1/L2 两种资产：用户、Agent 和 GPU 服务方始终使用同一种 `btck1s...` 钱包与 BTC-K。界面可在 BTC-K 与 SatK 两种显示之间切换；该按钮只改变显示单位。L2 收益不足 `10,000 SatK`（`0.0001 BTC-K`）时继续累计，达到门槛后才可上链，网络费由独立系统费用储备承担。

## 9. x402 开放机器支付协议兼容性与审计整改规范（实验性规范 Profile v2.2.0）

针对《BTCK第三次独立审计报告》指出的安全与架构审查意见，BTC-K AI-RPC 网关与 x402 机器支付体系已实施全量 P0/P1 强化（Hardened Profile v2.2.0）：

### 9.1 标准 x402 挑战与强签名验真流程
1. **账单登记与防白嫖（修复 C-01）**：网关维护活跃发票注册表（`invoices`），包含随机 Nonce、超时时间（TTL）与状态流转（PENDING → SETTLED → EXPIRED）。未由网关签发或已结算的发票凭证立即被驳回（HTTP 402），杜绝任何伪造账单白嫖算力可能。
2. **密码学强签名校验（修复 H-01）**：微支付凭据携带支付方公钥与 Schnorr BIP-340 签名，覆盖由 `invoice_id`、`amount_satk`、`treasury_addr`、`nonce` 和 `timestamp` 组成的规范摘要，确保支付凭证数学上不可伪造。
3. **生产环境直接充值接口禁用（修复 C-03）**：`/v1/deposit` 在生产模式下默认关闭并返回 HTTP 403 Forbidden，禁止未鉴权的余额修改。
4. **复合幂等键绑定（修复 H-02）**：幂等缓存以 `agent_stealth_address:model:idempotency_key` 进行复合隔离，杜绝跨账户与跨模型请求碰撞。
5. **共识级整数 SatK 结算（修复 H-06）**：全系统废除浮点数计价，统一采用 uint64 整数 SatK，从根源杜绝浮点数精度截断漏洞。

### 9.2 网关输出的标准响应头矩阵
* `WWW-Authenticate`: `L402 invoice="..."`, currency="SatK", amount="...", address="..."
* `X-Payment-Address`: 收款隐蔽地址（`btck1s...`，防链上关联）
* `X-Payment-Amount`: 精准结算金额（严格以 uint64 整数 SatK 聪K 计价）
* `X-Payment-Token`: `SatK`
* `X-Payment-Invoice`: 单次专属账单唯一哈希（由网关注册表严格校验）
* `X-Payment-Network`: `BTCK-BlockDAG`
* `X-Payment-Expires`: Unix 过期时间戳

## 10. 具身智能与物理机器人分层代理钱包技术架构（实验性规范 Profile v2.2.0）

随着人形机器人（Tesla Optimus、Figure 02、宇树 Unitree）、无人送货车与自动充电桩等**物理具身智能（Embodied AI）**的大爆发，机器人在物理世界的自主支付面临残酷现实：**物理拆机逆向私钥、模型幻觉挥霍资金，以及物理活动轨迹关联分析**。

BTC-K 官方 SDK（`btck_agent.robot_wallet`）在 v2.2.0 中完成了全面安全重构。

### 10.1 核心架构四重护甲（Hardened Profile）

| 维度 | 传统公链做法 | **BTC-K 具身智能专用钱包规范 (v2.2.0 强化版)** |
| :--- | :--- | :--- |
| **密钥硬件飞地隔离** | 纯软件明文保存，或由公开参数推导私钥（C-02 隐患） | **硬件飞地内部真随机生成（Fixes C-02）**：`HardwareEnclaveInterface` 内部由芯片硬件安全高熵随机数生成私钥且**永不导出**，外部仅能获取公钥并请求飞地内部签名，不可通过主地址/设备ID逆向推导 |
| **默认拒绝与三重预算** | 默认放行消费，无严格限额（H-03 隐患） | **默认拒绝（Default-Deny）+ 三重硬预算（Fixes H-03 & H-06）**：无主人有效签名 Delegation Pact 时严禁支出；严格要求 uint64 正整数 SatK；实施并发互斥锁保护的单笔上限、单日限额与终身授权总上限 |

from btck_agent import BTCKWallet, DelegationReceipt, RobotDelegatedWallet
